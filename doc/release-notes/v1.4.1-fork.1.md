# Resin v1.4.1-fork.1

This fork release is based on upstream v1.4.1, rebased onto the current
upstream master, and adds the platform TLS verification policy.

## Changes

- Rebased on upstream v1.4.1: proxy chains keep a stable relay binding for
  each exit node, and chain health feedback correctly attributes confirmed
  relay connection failures.
- Added per-platform HTTPS certificate verification policies with CA
  certificate management.
- The node pool now shows the current relay or an unassigned status,
  refreshed after manual probes.

## Platform HTTPS Certificate Verification

- Each custom Platform can verify upstream TLS with the system certificate
  store (the default), additionally trust an imported CA certificate, or
  explicitly skip certificate verification for exceptional upstreams.
- Skipping verification requires a reason and may carry an expiration; an
  expired policy automatically falls back to system verification. The
  built-in `Default` Platform always keeps strict verification enabled and
  cannot be relaxed.
- CA certificates are imported once and reused by any number of Platforms.
  Resin canonicalizes and deduplicates imported certificates by fingerprint,
  prevents deletion while a Platform still references them, never exposes the
  PEM material, and keeps an audit history of create, reuse, and delete
  events.
- Platform settings and their certificate verification policy are saved as
  one atomic action. Saving is protected by an optimistic version check, so
  a concurrent edit fails with a conflict instead of overwriting changes.
- Only confirmed node transport failures count against node health.
  Upstream TLS errors and ambiguous dial failures are attributed to the
  target instead of penalizing the relay node.
- Request logs record the verification outcome per request: the effective
  policy, policy version, CA bundle fingerprint, expired state, and failure
  attribution.
- The WebUI adds a certificate verification panel inside each Platform's
  configuration tab and a CA certificate management page.

## Upgrade Notes

> [!IMPORTANT]
> Starting this release, the state database is migrated from version 10 to
> 11 at startup. The migration adds `ca_bundles`, `ca_bundle_history`,
> `platform_tls_policies`, and `platform_tls_policy_history`, plus a
> `config_version` column on `platforms`.

> [!WARNING]
> Upgrading from the pre-rebase fork release (fork v1.3.0, the old
> `ghcr.io/killbus/resin:latest`): that release used migration number 10 for
> the platform TLS policy, so its state database is marked as version 10
> **without** the upstream `chain_proxy` / `chain_relay` columns. After
> starting this release, the first run stops with either a dirty
> `schema_migrations` record or a `no such column: chain_proxy` error.
> Stop Resin, then run in the state directory (for example via
> `docker run --rm --mount type=bind,source=/host/state/dir,dst=/data alpine
> sh -c "apk add --no-cache sqlite && sqlite3 /data/state.db 'ALTER TABLE
> subscriptions ADD COLUMN chain_proxy INTEGER NOT NULL DEFAULT 0 CHECK
> (chain_proxy IN (0, 1)); ALTER TABLE subscriptions ADD COLUMN chain_relay
> INTEGER NOT NULL DEFAULT 0 CHECK (chain_relay IN (0, 1) AND NOT (chain_proxy
> = 1 AND chain_relay = 1));'"):
>
> ```bash
> sqlite3 state.db "UPDATE schema_migrations SET dirty = 0;"
> sqlite3 state.db "
>   ALTER TABLE subscriptions ADD COLUMN chain_proxy INTEGER NOT NULL DEFAULT 0 CHECK (chain_proxy IN (0, 1));
>   ALTER TABLE subscriptions ADD COLUMN chain_relay INTEGER NOT NULL DEFAULT 0 CHECK (chain_relay IN (0, 1) AND NOT (chain_proxy = 1 AND chain_relay = 1));
> "
> ```
>
> Keep `version` at 11; do not roll it back to 10. Back up `state.db` first.

- Back up `<RESIN_STATE_DIR>/state.db` before upgrading.
- To downgrade to an earlier release, stop Resin and restore the pre-upgrade
  backup. Do not attempt to roll back the migrated database.
